# Local data deletion design

This document records the approved design and current implementation boundary for deleting Still's locally stored app data. The application now has a gated review, confirmation, cleanup, and fresh-workspace flow backed by a separate control journal and epoch-bound resource ownership. Browser simulations and automated checks exercise the flow. They do not prove native Keychain, filesystem, SQLite/WAL, notification-center, process-identity, backup, reinstall, or physical-media deletion; native identity code has not been compiled into a signed app or validated on a device.

## User promise and limits

The user reviews a private, aggregate inventory, types `DELETE`, then confirms deletion in a separate action. A review expires after five minutes. Canceling the review has no mutation and leaves the mounted workspace—including unsaved content—intact.

The deletion covers tracked local app records: notes and context; action history and private recovery copies; recordings and SDK-managed cache copies; locally stored account/provider credentials; and pending or delivered Still notifications. Legacy OAuth keys that were never recorded in the ownership ledger cannot be enumerated. The UI must say **tracked data with legacy limits** rather than implying that every historical key is known or deleted.

Deletion cannot remove an exported, iCloud, shared, or other copied file; retract email or calendar events already sent or saved; erase data already submitted to a provider; or guarantee physical-media or operating-system-backup erasure. Do not claim any of those outcomes.

## Flow and app lifecycle

1. Privacy review is presented over the mounted workspace. The user sees only category totals and fixed retention limits—never archive contents, secret values, token references, file paths, quarantine payloads, or credential identifiers.
2. The user types `DELETE` and chooses a separate confirmation. The engine must revalidate the five-minute plan and ownership before beginning any I/O. Canceling a prepared review clears only that review plan; canceling before durable begin does not change stored data.
3. Only after durable deletion has begun does the app unmount the workspace and display a dedicated cleanup screen. No ordinary workspace action, recording, credentials, OAuth, model request, or foreground hook may run while cleanup is incomplete.
4. Cleanup shows fixed categories and verified/working/paused/failed status. It retries only unfinished known cleanup steps. The screen stays in place until every known step is verified gone; a failure never opens the normal workspace.
5. Completion retains only a minimal nonpersonal epoch/completion summary. The user explicitly opens a newly keyed workspace with default settings, no grants, no executable approvals, and Speech disabled.

## Runtime and concurrency constraints

Full deletion is available only in the dedicated `com.still.voiceassistant` iOS custom build with the process-stable identity module. Expo Go or a missing identity module must show an unavailable explanation and no delete action. The native process identity combines a launch UUID and the bundle identity. A lost I/O lease in the same process stays blocked until a full process restart; another process may reconcile only old local destinations and may not claim remote cancellation.

On web, require both a secure context and Web Locks. Keep the lock for the actual asynchronous operation; never use an expiring lease or steal a lock after a timeout. If these guarantees are unavailable, disable full cleanup.

The control journal is independent of user data: SQLite `still-privacy-control.db` on native and IndexedDB `still-privacy-control-v1` on web. Each plan uses a UUID epoch and CAS revision. Before I/O, persist a strict ownership intent containing only namespace and UUID token. Writer leases remain held until the actual I/O promise settles. Process at most 16 cleanup steps in a pass and cap inventory at 5,130 targets. Cleanup makes no model/network calls.

## Review and failure behavior

The inventory contains aggregate category counts only. Its review is valid for five minutes; confirmation rechecks that revision and capability state. Storage mutation must begin only after the durable journal transition. Once deletion starts, any paused or failed result keeps the cleanup screen mounted and blocks ordinary app use. Retry is explicit and resumes only safe, unfinished steps. A completion page appears only when every known target is verified absent. The retained summary must not contain personal data.

Existing scheduled reminders may fire until their notification requests are verified removed. Provider-side data, sent messages, and calendar events remain outside the deletion boundary. Legacy untracked keys, inaccessible platform-owned copies, and any target the runtime cannot verify must be disclosed as limits, not represented as successful cleanup.

## Current verification boundary

The production app checks the privacy service before creating/loading the normal controller, reading credentials, or starting foreground hooks. The workspace uses one immutable runtime/session binding for controller resources and audio boundaries. Writer and cleanup arbitration spans the actual asynchronous I/O promises; unsupported runtime identity or web locking fails closed. The dedicated iOS identity module is present and autolinking was detected, but its Swift implementation has not been compiled in a native build.

Closed tests and browser simulations validate review, cancellation before begin, cleanup progress, blocked/paused states, retry, ambiguous confirmation recovery, and a newly keyed empty workspace. The `privacy-cleanup` preview uses fictional, in-memory stores and closed service adapters. At 1280×720, browser QA verified that cancel preserved unsaved search and note data; lowercase `delete` did not enable confirmation; a successful flow removed the old notes and task from the fresh workspace; a paused cleanup blocked ordinary workspace controls until retry; a lost confirmation response offered status retry without a second confirmation; and paused startup stayed gated until retry. Browser console error logs were empty. Proofs are in `docs/screenshots/privacy-cancel-retained.png`, `privacy-review.png`, `privacy-complete.png`, `privacy-fresh.png`, `privacy-paused.png`, `privacy-unknown-confirmation.png`, and `privacy-paused-startup.png`. This was desktop-sized browser QA, not a mobile viewport or native-device test.

The UI reports aggregate categories with **tracked data with legacy limits** coverage. Historical OAuth keys that were never entered in the ownership ledger cannot be enumerated, so completeness for those keys is not claimed. The fixed retention notice explains that exported/iCloud/shared copies, already sent or saved email/calendar actions, and provider-submitted data remain outside the deletion boundary; physical-media and operating-system-backup erasure cannot be promised. A completed receipt contains only a minimal nonpersonal summary. The cleanup engine makes no provider or model requests.
