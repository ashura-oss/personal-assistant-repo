## Unsigned ARM64 build workflow

The repository includes a manually dispatched GitHub Actions workflow at `.github/workflows/ios-unsigned-device.yml`. It runs on an Apple Silicon `macos-26` runner and calls the same `scripts/build-unsigned-ios.sh` used for a local Mac build. The script verifies Xcode 26.4+ and Node 22.13+ (SDK 57 minimums [in Expo's SDK reference](https://docs.expo.dev/versions/latest/)), installs the npm lockfile and checked-in patch, runs project checks, generates the iOS project, verifies Expo autolinking, installs CocoaPods, and builds an arm64 Release `iphoneos` app with signing disabled. It refuses to clean an existing `ios/` directory, so each build needs a fresh checkout. It checks the expected build bundle ID, executable architecture, and bundled JavaScript, then packages the full app directory inside `Payload/` for a five-day Actions artifact. The build-log match for `StillPrivacyModule.swift` records a source-build entry only; it does not prove the module is linked into the final executable or works at runtime. For a friend-owned Mac, see [the Mac build handoff](MAC_FRIEND_BUILD.md).

This output is **unsigned** and cannot launch until signed. AltStore's official provisioning code constructs a new app identifier by appending the signing-team identifier to the parent bundle ID when registering an app [in its provisioning-profile flow](https://github.com/altstoreio/AltStore/blob/develop/AltStore/Operations/FetchProvisioningProfilesOperation.swift). The privacy runtime source now accepts only `com.still.voiceassistant` or that exact ten-character uppercase-alphanumeric suffix form, preserving the full ID for identity checks. The Windows direct-sideload result and runtime behavior remain unverified. AltServer documents direct IPA sideloading and seven-day reinstallation for those apps [in its release notes](https://github.com/altstoreio/FAQ/blob/main/release-notes/altserver.md); this does not establish that Still launches correctly after signing.

The app's runtime identity remains deliberately strict. The source compatibility predicate is implemented and covered by tests, but the native module has not been compiled or exercised with an AltStore-signed bundle ID. Even a successful compile or IPA package would not prove the module is linked, the re-signed app launches, or device features work. The [iOS validation matrix](IOS_VALIDATION.md) remains the record for those checks.

GitHub-hosted builds require this source tree in a GitHub repository; the artifact is stored by Actions. This workspace has no configured remote. No repository was created, source uploaded, workflow dispatched, or build artifact produced. The workflow has not been build-verified. If the source must stay off GitHub, a trusted Mac or another authorized build host is needed.

The workflow sets `EXPO_NO_DOTENV=1`; it does not read `.env`, provider keys, or signing credentials. OAuth callbacks depend on public native client ID/redirect values not supplied to the workflow. No private key is included in the artifact.

## Custom iOS build requirement

Still requires its local `StillPrivacy` Expo module to obtain the process-stable runtime identity used by full privacy cleanup. Expo Go does not contain this local module and cannot validate that path. A development or distribution build made from this project is required. OAuth redirect changes also require a new native build. Background mail refresh uses the installed SDK's official config-plugin chain to configure iOS background modes; the app registers its task only after explicit enablement. Static review is not proof of task registration or execution.

The `eas.json` profiles currently mean:

- `development`: development client plus internal distribution. After installing it, run `npx expo start --dev-client`; Metro is required to serve the JavaScript bundle.
- `preview`: internal distribution without a development client. The JavaScript bundle is embedded in the build; it does not require Metro.
- `production`: store distribution configuration. It still requires Apple signing and release review; no production build or submission has occurred.

## Phase 41 · mail Batch source verification and proof limits

Account disconnect/replacement revokes credentials, advances generation, and invalidates pending approvals/plans while retaining Batch history and receipts. Ordinary provider Inbox pages, selected-text refreshes, and deletion observations can still commit fresh mailbox metadata/body/cursors/new-mail state and invalidate ordinary pending drafts. Affected uncertain Batch jobs, receipts, and accounting remain tied to their old context and cannot authorize actions against fresh data. Private quarantine retains all affected Mail context for provider observation without matching untrusted IDs; other affected jobs are redacted, and explicit content deletion remains blocked there even when no validated receipt or proposal is available. Explicit destructive content erasure (job, note, guidance, or source cleanup) remains blocked by uncertain dispatch or private quarantine. A narrowly fenced late acknowledgement may retain metadata for an already-issued mail POST after revocation; queued receipt updates are fenced by privacy epoch, bootstrap generation, and job ownership, and cannot restore removed content or bypass privacy/bootstrap/job-removal checks. Batch-linked proposals carry `batchJobId`; the dispatch receipt carries `MailReplyBatchBinding` (`jobId`, `provenanceCanonical`) exactly when it is Batch-linked, and ordinary non-Batch receipts omit it. This is structural consistency metadata only, not cryptographic attestation or authority; modifying both the binding and provenance is outside its check scope, while current private job/source/approval checks remain authoritative.

The App source now wires an explicit OpenRouter Batch mail-reply path: Submit may create a delayed paid job, Check is an explicit status GET only, a completed result requires a fresh source read and read-only review, and Create draft consumes a one-use plan to create a local proposal. Normal approval and the later mailbox draft action remain separate. Batch-linked reply proposals are immutable; a separate manual reply can still be written. When the OpenRouter key is absent, local mail-job history remains available while paid Submit and remote Check stay disabled. Saved request/result deletion retains a compact accounting receipt in global history; any created proposal is invalidated but its copy remains. Uncertain deletion is not presented as success and blocks further destructive cleanup. Archive imports restore no job, result, source binding, or Batch authority.
